# FEATURE 1 — INTELLIGENT AUTO-PR SYSTEM WITH BATCH ISSUE RESOLUTION

## Overview
When any analysis agent (Code Analysis, Security, QA) detects issues in a pushed repository, instead of simply blocking the pipeline, the system must: collect ALL issues from ALL agents simultaneously, resolve each issue programmatically using Claude, create one branch per issue category, commit the fixes to those branches, and then open all PRs at once to the original repository. When the repo owner merges any PR, a GitHub webhook event triggers automatic branch deletion. The pipeline must never halt mid-analysis — it must complete the full analysis pass across all agents before generating any PR.

---

### Feature 1 — Phase 1: Auto-PR Service Foundation

Create a new file `app/services/auto_pr_service.py`. In this file, build a class `AutoPRService` that is initialized with `github_token: str`, `repo_full_name: str`, `clone_url: str`, and `base_branch: str` (defaulting to "main"). The `__init__` method must create an `httpx.AsyncClient` with `base_url="https://api.github.com"`, set the Authorization header to `token {github_token}`, and set Accept to `application/vnd.github.v3+json`. Also store a `git_service` instance from `app.services.git_service.GitService`. Create a dataclass `IssueBundle` in `app/services/auto_pr_service.py` with fields: `category: str` (e.g. "security", "code-quality", "test-failures"), `issues: list[dict]`, `file_patches: list[dict]` (each patch has keys: `file_path`, `original_content`, `fixed_content`, `explanation`), `branch_name: str`, `pr_title: str`, `pr_body: str`, and `pr_number: int | None = None`. This dataclass will represent a single batched PR containing all fixes for one category. Add a module-level logger using `get_logger("auto_pr_service")` and import all required modules: `httpx`, `asyncio`, `json`, `base64`, `dataclasses`, `typing`, and the Anthropic client. The class must also have a `self.created_branches: list[str] = []` attribute to track all branches opened during a pipeline run so they can be cleaned up later.

---

### Feature 1 — Phase 2: Full Repository Analysis Without Early Exit

Create a new file `app/agents/full_scan_orchestrator.py`. This class `FullScanOrchestrator` inherits from `BaseAgent` and accepts `repo_path: str`, `diff_text: str`, and `pipeline_run_id: str`. The `execute(self) -> dict` method must run all three analysis agents — `CodeAnalysisAgent`, `SecurityAgent`, and `QAAgent` — concurrently using `asyncio.gather(code_agent.execute(), security_agent.execute(), qa_agent.execute(), return_exceptions=True)` so that even if one agent raises an exception it does not prevent the others from completing. After gather returns, iterate over all three results: if a result is an `Exception` instance, log it with `self.logger.error` and store `{"error": str(result), "skipped": True}` for that agent — never re-raise. Merge all findings from all three agents into a single `combined_issues: dict` with keys `"code_issues"`, `"security_issues"`, `"qa_issues"`, each containing the full agent result dict or the error fallback dict. The method must save a `pipeline_artifact` of type `"full_scan_combined"` containing the `combined_issues` dict, then return the combined dict. This guarantees the pipeline always does a complete full-pass analysis regardless of individual agent failures, and the combined result becomes the sole input to the PR generation phase that follows.

---

### Feature 1 — Phase 3: Claude-Powered Issue Resolution and Patch Generation

Inside `app/services/auto_pr_service.py`, add an async method `generate_fix_patches(self, issues: list[dict], repo_path: str, category: str, anthropic_client) -> list[dict]` that takes a list of raw issues, reads the actual file contents from disk for each affected file, and calls Claude to generate concrete code fixes. For each unique file referenced in the issues list, read the file content using `open(os.path.join(repo_path, file_path)).read()` and pass both the original content and the list of issues affecting that file to Claude using the following system prompt written verbatim: "You are an expert software engineer. You will receive a source file and a list of issues found in it. Your job is to return a corrected version of the entire file that resolves all listed issues. Do not add placeholder comments or TODOs — make real, working fixes. Return ONLY valid JSON in this exact schema: `{\"file_path\": string, \"fixed_content\": string (the complete corrected file), \"explanation\": string (what was changed and why), \"changes_made\": [string]}`. The fixed_content must be the complete file, not a diff or snippet. Return ONLY valid JSON." Pass `max_tokens=4000` to handle large files. After receiving the response, parse it and validate that `fixed_content` is a non-empty string. If Claude returns invalid JSON or empty content, log the error and return the original file unchanged with an explanation of `"AI fix generation failed, manual review required"`. Collect all successful patch dicts into a list and return it. This method is the core of the intelligent fix generation — every issue gets an actual code fix, not just a report.

---

### Feature 1 — Phase 4: Branch Creation and Commit Push

Inside `app/services/auto_pr_service.py`, add an async method `create_branch_with_fixes(self, bundle: IssueBundle, run_id: str) -> str` that performs the complete Git workflow for one `IssueBundle`. The method must first call `GET /repos/{repo_full_name}/git/ref/heads/{base_branch}` to get the current HEAD SHA of the base branch. Then call `POST /repos/{repo_full_name}/git/refs` with body `{"ref": "refs/heads/{bundle.branch_name}", "sha": "{head_sha}"}` to create the new branch — if the branch already exists (409 response), append `-{run_id[:6]}` to make it unique and retry. For each patch in `bundle.file_patches`, call `GET /repos/{repo_full_name}/contents/{file_path}?ref={bundle.branch_name}` to get the current file's SHA (needed for update), then call `PUT /repos/{repo_full_name}/contents/{file_path}` with body `{"message": "fix({category}): resolve {issue_type} in {file_path}", "content": base64.b64encode(fixed_content.encode()).decode(), "sha": file_sha, "branch": bundle.branch_name}` to commit the fix directly to the new branch. After all files are committed, append `bundle.branch_name` to `self.created_branches`. Return the branch name. Handle all `httpx.HTTPStatusError` exceptions by logging the full response body and re-raising with context so the caller can skip this bundle and continue with others.

---

### Feature 1 — Phase 5: Batch PR Creation

Inside `app/services/auto_pr_service.py`, add an async method `create_pr(self, bundle: IssueBundle) -> int` that calls `POST /repos/{repo_full_name}/pulls` with body `{"title": bundle.pr_title, "body": bundle.pr_body, "head": bundle.branch_name, "base": self.base_branch, "maintainer_can_modify": True}`. The PR body must be generated using a helper method `_build_pr_body(bundle)` that formats a rich markdown body including: a summary table of all issues fixed (columns: File, Line, Issue Type, Fix Applied), a "Changes Made" section listing each file modified, a "How to Review" section, and a footer `"🤖 Auto-generated by ORION Pipeline — Run ID: {run_id}"`. After creating the PR, set `bundle.pr_number` to the returned PR number. Return the PR number. Then create the main batch method `open_all_prs(self, combined_issues: dict, repo_path: str, run_id: str, anthropic_client) -> list[IssueBundle]` that: groups issues by category (security gets its own bundle, code-quality gets its own, test-failures gets its own), calls `generate_fix_patches` for each category concurrently using `asyncio.gather`, then calls `create_branch_with_fixes` for each bundle sequentially (to avoid GitHub rate limits), then calls `create_pr` for all bundles concurrently using `asyncio.gather`, and returns the full list of `IssueBundle` objects with PR numbers set. All PRs are opened in one batch — this is the core design requirement.

---

### Feature 1 — Phase 6: PR Acceptance Webhook and Automatic Branch Deletion

In `app/api/routes/webhook.py`, add a new endpoint `POST /api/v1/webhook/github/pr` that handles GitHub Pull Request events. The endpoint must validate the HMAC signature using the same `get_validated_github_payload` dependency already in place. Parse the body as JSON and check `payload["action"]` — only process actions `"closed"` where `payload["pull_request"]["merged"] == True`. Extract `repo_full_name = payload["repository"]["full_name"]`, `branch_name = payload["pull_request"]["head"]["ref"]`, and `pr_number = payload["pull_request"]["number"]`. Query the database for any `PipelineArtifact` of type `"auto_pr_registry"` whose `content` JSON contains a `branch_name` matching the closed branch. If found, call `github_service.delete_branch(repo_full_name, branch_name)` which must be a new method in `app/services/github_service.py` that calls `DELETE /repos/{repo_full_name}/git/refs/heads/{branch_name}`. Log the deletion. If the branch does not exist (404), log and continue silently. Update the artifact record to mark that branch as `"merged_and_deleted": True`. Also add a new `PipelineArtifact` type `"auto_pr_registry"` that is written by `open_all_prs` containing the full list of all created branches and their associated PR numbers, stored as `{"branches": [{"branch_name": str, "pr_number": int, "category": str, "merged": bool, "deleted": bool}]}` — this is the registry used by the webhook to know which branches belong to ORION.

---

### Feature 1 — Phase 7: Wire Into Orchestrator

In `app/agents/orchestrator.py`, modify the `execute_pipeline` method to integrate the auto-PR system. After Stage 3 (Security) and Stage 4 (QA Testing) complete, instead of immediately blocking the pipeline, collect their results. If any of the three agents (Code Analysis, Security, QA) have non-passing results, do the following before setting any "blocked" status: instantiate `AutoPRService(settings.github_token, run.repo_full_name, run.clone_url, run.branch)`, call `await auto_pr_service.open_all_prs(combined_issues, repo_path, pipeline_run_id, self.anthropic_client)`, save the returned list as a `"auto_pr_registry"` artifact, update the run status to `"blocked_with_prs_sent"` (add this as a valid status in the PipelineRun model), set `run.error_message` to a summary like `"Pipeline blocked. {N} fix PRs opened: {pr_urls}"`, and call `slack_service.send_pipeline_blocked` with the PR URLs included. The pipeline should NOT proceed to deployment if blocked — but it should always finish analysis and always send all PRs before reporting the block. Add `"blocked_with_prs_sent"` to the valid statuses list in `app/models/pipeline_run.py`.

# FEATURE 2 — NGINX REVERSE PROXY CONFIGURATION

## Overview
All external traffic to ORION must go through an Nginx reverse proxy that handles SSL termination, load balancing between the FastAPI app and the Celery Flower dashboard, rate limiting on the webhook endpoint (to prevent webhook abuse), request buffering, and security headers. Nginx runs as a Docker service alongside the existing stack.

---

### Feature 2 — Phase 1: Nginx Docker Service and Directory Structure

Create a top-level directory `nginx/` in the project root. Inside it create three files: `nginx.conf` (main config), `conf.d/orion.conf` (server block), and `ssl/.gitkeep` (placeholder for SSL certificates). In `docker-compose.yml`, add a new service `nginx` using image `nginx:1.25-alpine`, with ports `"80:80"` and `"443:443"` mapped, volumes mounting `./nginx/nginx.conf:/etc/nginx/nginx.conf:ro`, `./nginx/conf.d:/etc/nginx/conf.d:ro`, and `./nginx/ssl:/etc/nginx/ssl:ro`, depends_on the `app` service, and restart policy `unless-stopped`. Add a healthcheck: `test: ["CMD", "nginx", "-t"]`, interval 30s, timeout 10s, retries 3. The Nginx service must be on the same Docker network as the app service — define a custom bridge network called `orion_net` in the docker-compose networks section and attach all services (postgres, redis, app, worker, nginx) to it. This establishes the network topology before any config is written.

---

### Feature 2 — Phase 2: Main Nginx Configuration

Write `nginx/nginx.conf` with the following complete configuration. Set `worker_processes auto` and `error_log /var/log/nginx/error.log warn`. In the `events` block set `worker_connections 1024` and `use epoll`. In the `http` block: set `sendfile on`, `tcp_nopush on`, `tcp_nodelay on`, `keepalive_timeout 65`, `types_hash_max_size 2048`, `server_tokens off` (hides Nginx version in headers), `client_max_body_size 10M` (webhook payloads can be large), `client_body_timeout 12s`, `client_header_timeout 12s`, `send_timeout 10s`. Define a `log_format` named `orion_log` that captures: `$remote_addr`, `$request`, `$status`, `$body_bytes_sent`, `$http_referer`, `$http_user_agent`, `$request_time`, and `$upstream_response_time` — this structured format feeds into the monitoring agent's log analysis. Set `access_log /var/log/nginx/access.log orion_log`. Define a `limit_req_zone $binary_remote_addr zone=webhook_limit:10m rate=10r/m` to rate-limit webhook callers to 10 requests per minute per IP. Define a second zone `limit_req_zone $binary_remote_addr zone=api_limit:10m rate=60r/m` for general API rate limiting. Include `conf.d/*.conf` at the end of the http block.

---

### Feature 2 — Phase 3: Server Block and Upstream Configuration

Write `nginx/conf.d/orion.conf` with the complete server blocks. First define an `upstream orion_app` block with `server app:8000` and `keepalive 32`. Define an `upstream orion_flower` block with `server flower:5555`. Write a server block for port 80 that immediately redirects all HTTP traffic to HTTPS using `return 301 https://$host$request_uri`. Write the main server block listening on port 443 with `ssl_certificate /etc/nginx/ssl/fullchain.pem`, `ssl_certificate_key /etc/nginx/ssl/privkey.pem`, `ssl_protocols TLSv1.2 TLSv1.3`, `ssl_ciphers ECDHE-RSA-AES256-GCM-SHA512:DHE-RSA-AES256-GCM-SHA512:ECDHE-RSA-AES256-GCM-SHA384`, `ssl_prefer_server_ciphers on`, `ssl_session_cache shared:SSL:10m`, `ssl_session_timeout 10m`. Add security headers: `add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload"`, `add_header X-Frame-Options DENY`, `add_header X-Content-Type-Options nosniff`, `add_header X-XSS-Protection "1; mode=block"`, `add_header Referrer-Policy "strict-origin-when-cross-origin"`. Define location blocks: `/api/v1/webhook/` uses `limit_req zone=webhook_limit burst=5 nodelay` and proxies to `orion_app`. `/api/` uses `limit_req zone=api_limit burst=20 nodelay` and proxies to `orion_app`. `/flower/` proxies to `orion_flower` with `auth_basic "ORION Monitoring"` and `auth_basic_user_file /etc/nginx/.htpasswd`. `/` proxies to `orion_app`. All proxy locations must set `proxy_set_header Host $host`, `proxy_set_header X-Real-IP $remote_addr`, `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for`, `proxy_set_header X-Forwarded-Proto $scheme`, `proxy_http_version 1.1`, `proxy_set_header Connection ""`, and `proxy_read_timeout 300s` (long timeout for pipeline webhook processing).

---

### Feature 2 — Phase 4: Self-Signed SSL Certificate Script and Dev Mode Fallback

Create a shell script `nginx/generate_dev_ssl.sh` that uses `openssl req -x509 -nodes -days 365 -newkey rsa:2048` to generate a self-signed certificate stored at `nginx/ssl/fullchain.pem` and `nginx/ssl/privkey.pem` with subject `/C=US/ST=Dev/L=Dev/O=ORION/CN=localhost`. Make the script executable with `chmod +x`. Also create `nginx/conf.d/orion_dev.conf` (an alternative config for development) that has the same upstream and location blocks but listens on port 80 only (no SSL), and does not include rate limiting. Add a `Makefile` at the project root with targets: `make dev-nginx` (copies orion_dev.conf, removes orion.conf, runs docker-compose up nginx), `make prod-nginx` (generates SSL if not exists, uses orion.conf), `make nginx-reload` (runs `docker-compose exec nginx nginx -s reload`), and `make nginx-logs` (runs `docker-compose logs -f nginx`). Update `.env.example` to add `NGINX_MODE=development` and `FLOWER_BASIC_AUTH_USER=admin` and `FLOWER_BASIC_AUTH_PASSWORD=orion_admin`. Write a Python script `scripts/generate_htpasswd.py` that reads `FLOWER_BASIC_AUTH_USER` and `FLOWER_BASIC_AUTH_PASSWORD` from env and writes `nginx/.htpasswd` using `passlib.hash.apr_md5_crypt`.

# FEATURE 3 — MULTIMODAL AGENT SYSTEM

## Overview
ORION must be extended with a suite of multimodal agents that can process not just text but also images (screenshots of errors, architecture diagrams), structured data (payment CSVs, log files), and binary artifacts (Docker build logs, GitHub Actions log zip files). These agents handle five specific domains: Payment System analysis, Git/Server log analysis (timeouts, build errors), GitHub log file parsing, Dockerfile error detection, and Production issue triage. Each agent is multimodal — it accepts text, images, and file uploads and passes them to Claude's vision and document capabilities.

---

### Feature 3 — Phase 1: Multimodal Base Agent and File Handler

Create `app/agents/multimodal/` directory with `__init__.py`, `base_multimodal_agent.py`, `payment_agent.py`, `log_analysis_agent.py`, `github_log_agent.py`, `dockerfile_agent.py`, and `production_triage_agent.py`. In `base_multimodal_agent.py`, create class `BaseMultimodalAgent(BaseAgent)` that extends the existing `BaseAgent`. Add an `__init__` that accepts an additional parameter `artifacts: list[dict]` where each artifact is `{"type": "image"|"text"|"pdf"|"csv"|"log", "content": bytes|str, "filename": str, "mime_type": str}`. Add a protected method `_build_multimodal_message(self, text_prompt: str) -> list` that converts the `self.artifacts` list into the Anthropic messages API format: for type "image", build `{"type": "image", "source": {"type": "base64", "media_type": mime_type, "data": base64.b64encode(content).decode()}}`. For type "text", "csv", or "log", build `{"type": "text", "text": f"FILE: {filename}\n{content[:50000]}"}` (truncate large files to 50k chars). For type "pdf", build `{"type": "document", "source": {"type": "base64", "media_type": "application/pdf", "data": base64.b64encode(content).decode()}}`. The method returns a list of content blocks with the text_prompt as the final block. Override `_call_claude_multimodal(self, system_prompt: str, text_prompt: str, max_tokens: int = 3000) -> tuple[str, int]` to call `anthropic_client.messages.create` with `messages=[{"role": "user", "content": self._build_multimodal_message(text_prompt)}]` and the system prompt. Also add a new FastAPI endpoint `POST /api/v1/multimodal/analyze` in a new router file `app/api/routes/multimodal.py` that accepts `multipart/form-data` with fields `agent_type: str`, `pipeline_run_id: str | None`, and one or more file uploads, instantiates the correct agent based on `agent_type`, and returns the analysis result as JSON.

The `execute(self) -> dict` method must: first build a multimodal message from all provided artifacts (which may include CSV files of transaction logs, screenshots of error dashboards, or JSON webhook payloads), call Claude with the following system prompt verbatim: "You are a payment systems engineer. Analyze the provided payment data, logs, screenshots, and webhook payloads. Identify all failed transactions, error patterns, potential fraud indicators, and webhook delivery failures. ### Feature 3 — Phase 3: Git and Server Log Analysis Agent

Create `app/agents/multimodal/log_analysis_agent.py` with class `LogAnalysisAgent(BaseMultimodalAgent)`. This agent processes server logs, Git operation logs, build logs, and timeout traces. The constructor accepts `log_type: str` which must be one of: `"server_timeout"`, `"build_error"`, `"git_operation"`, `"deployment_crash"`, `"memory_leak"`. The `execute(self) -> dict` method assembles all provided log file artifacts, then calls Claude with a dynamically constructed system prompt based on `log_type`. For `"server_timeout"`: the system prompt instructs Claude to identify which endpoints are timing out, what database queries are slow, whether connection pool exhaustion is occurring, and produce a fix plan. For `"build_error"`: identify the exact line causing the build failure, missing dependencies, incompatible versions, and suggest the exact `pip install` or `apt-get` fix. For `"git_operation"`: identify merge conflicts, detached HEAD states, corrupted refs, and provide the exact git commands to resolve. For `"memory_leak"`: identify which process or function is leaking, estimated leak rate per hour, and whether a restart schedule is needed. All log types return the same JSON schema: `{"log_type": string, "root_cause": string, "affected_components": [string], "error_timeline": [{timestamp, event, severity}], "exact_fix_commands": [string], "preventive_measures": [string], "severity": string, "estimated_resolution_time_minutes": int, "summary": string}`. Truncate each log file to the last 10,000 lines before passing to Claude since older log entries are rarely relevant to active issues.

# FEATURE 4 — SYSTEM D SERVER (SYSTEMD SERVICE MANAGEMENT)

## Overview
ORION must be deployable as a set of `systemd` services on a Linux server (Ubuntu 22.04 / Debian 12) for production deployments that do not use Docker. This means creating `.service` unit files for the FastAPI app, the Celery worker, the Celery beat scheduler, and the Nginx proxy, along with an installation script, a management CLI, a health-monitoring daemon that auto-restarts crashed services, and integration with `journald` for centralized log collection that feeds into ORION's own monitoring agent.

---

### Feature 4 — Phase 1: Systemd Unit Files

### Feature 4 — Phase 4: Journald Log Integration and ORION Log Feed
