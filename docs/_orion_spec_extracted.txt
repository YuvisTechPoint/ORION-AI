1. Executive Summary
ORION (Binary-v2) is a multi-stack, AI-assisted software delivery platform. Its current implementation comprises three independent pipeline stacks (Canonical DevOps, ORION CI/CD and the DevOps Platform), a Command Hub, shared text-analysis utilities, multimodal analysis agents, gate fusion, service level objective (SLO) computation, audit trails, role-based access control, Auto-PR remediation and Prometheus-based observability. The baseline is materially beyond a conventional CI/CD pipeline: hard security gates cannot be overridden by a language model, every agent persists structured artifacts, webhook delivery is idempotent, and pipelines are resumable at stage boundaries.
This document consolidates the master agent reference, the product README, the advanced feature expansion report and the phased implementation roadmap into a single authoritative specification. It defines the target product, the architecture required to reach it, a persistent memory architecture for agents and operators, a catalog of advanced features and functions, governance and security controls, and a sequenced delivery plan with measurable exit criteria.
Strategic position. ORION is positioned as an AI-Native Software Delivery and Reliability Control Plane: an open-source platform that analyzes code, predicts change risk, validates security and quality, orchestrates progressive deployments, monitors production, investigates incidents and safely automates remediation, while preserving deterministic gates ahead of any model-generated decision.

2. Purpose, Scope and Audience
2.1 Purpose
This document specifies what ORION is, what it must become, how it is structured and how it will be delivered. It is intended to serve as the single reference for architecture decisions, implementation planning, security review and contributor onboarding for the open-source project.
2.2 Audience
Maintainers and contributors who implement features and need binding architectural rules.
Platform and SRE engineers who operate ORION and require operational, security and reliability specifications.
Security and compliance reviewers who assess controls, trust boundaries and evidence production.
Evaluators and adopters who assess project maturity, roadmap credibility and engineering discipline.
2.3 Scope
In scope: the three pipeline stacks, Command Hub, shared libraries, agents, memory, policy, governance, security, observability, release engineering, incident management, developer experience, data model, configuration, testing and the delivery roadmap.
Out of scope for this release of the document: managed SaaS hosting, a proprietary commercial edition, and replacement of the three-stack topology with a single monolith. The independent stacks are retained; integration is achieved through adapters and a control plane.
2.4 Normative language
The words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as defined in RFC 2119. Requirements phrased with MUST are mandatory for acceptance of the relevant phase.
2.5 Assumptions
The current implementation is the baseline; no capability is assumed to exist solely because it is documented.
Python 3.11 or later and Node 20 or later remain the primary runtimes.
PostgreSQL and Redis are available for production deployments; SQLite remains acceptable for local development only.
The LLM provider is Anthropic Claude through the existing client abstraction; the architecture MUST remain provider-neutral at the interface level.

3.3 Established strengths
Hard-rule gating: scanner severity from Bandit and pip-audit cannot be downgraded by the model.
Artifact-first design: each agent persists structured JSON; gates read artifacts, not conversational output.
Heuristic fallback: pipelines complete without an API key through deterministic logic.
Webhook idempotency through a delivery ledger.
Operator controls: retry, resume (checkpoint), cancel, audit trail and manual approval.
Cross-stack parity for gate fusion, SLO computation, SLO alerting and text analysis.
Observability: /health, /ready and /metrics on every stack, Grafana dashboard and Slack alerting.
Multimodal agents: log, GitHub Actions, git history, payment, Dockerfile and production triage.
Security hygiene: secret redaction and truncation before every LLM call, rate limiting and multi-key RBAC.

4. Strategic Positioning and Design Principles
4.1 Product definition
ORION is an autonomous DevSecOps and SRE platform for the full loop: Repository, Intelligence, Code/Security/QA, Supply Chain, Performance, Approval, Deployment, Verification, Monitoring, Incident Response, Remediation, Audit and Learning.
4.2 Design principles
Table 5. Binding design principles
Principle
Statement
Fail closed
Security-critical decisions MUST deny on error, timeout or uncertainty. Scanner severity MUST NOT be reduced by model output.
Deterministic before probabilistic
Hard rules and scanners run first. The model explains, prioritizes and proposes; it does not override.
Evidence over assertion
Every autonomous decision MUST cite artifacts. Statements without evidence references MUST NOT enter a postmortem, approval record or memory write.
Artifacts as source of truth
Structured, versioned, schema-validated artifacts are authoritative. Chat output is never a gate input.
Policy-bounded autonomy
Agent capability is granted by declarative policy and permission manifest, never assumed.
Untrusted input
Repository content, logs, pull request text and uploads are data, never instructions.
Backward compatibility
Existing endpoints and behavior MUST be preserved; changes use adapters and versioned contracts.
Independent stacks, shared contracts
Stacks remain deployable alone; integration is by contract (resource model, events, correlation).
Observable by default
Every component emits metrics, structured logs and traces carrying correlation identifiers.
Depth over breadth
Features are complete when persisted, authorized, observable, tested and documented.

5.4 Deployment topology
TLS terminates at an edge proxy (nginx or cloud load balancer, TLS 1.2 or later). Internal traffic remains within a private network with optional mutual TLS. Stateless API containers scale horizontally; Celery workers scale by queue depth; PostgreSQL runs with TLS and provider-managed disk encryption; Redis is configured with persistence appropriate to its role (cache versus stream). Agent sandboxes execute on a separate worker pool with no production credentials and restricted egress.
5.5 Architecture decision records
Every decision that changes a boundary, contract or dependency MUST be recorded as an Architecture Decision Record in docs/adr/ with context, decision, alternatives and consequences. The first records to be written are: unified resource identifier format, event backbone selection, vector store selection, policy language selection and tenancy model.
6. Memory Architecture
6.1 Objectives
The platform currently has memory only in the canonical stack (SQLiteAgentMemoryStore, HybridFileRetriever). The target is a single governed Memory Gateway, available to all stacks, that allows agents and operators to recall prior pipelines, incidents, deployments, remediation outcomes and organizational knowledge, while preventing leakage across tenants, secrets persistence and memory poisoning.
Table 8. Memory requirements
ID
Requirement
MEM-01
All memory access MUST pass through the Memory Gateway; agents MUST NOT access stores directly.
MEM-02
Every record MUST carry tenant, namespace, provenance, confidence, trust level, created and expiry timestamps and a content hash.
MEM-03
Secrets MUST be redacted before any write; the write path MUST fail closed if redaction fails.
MEM-04
Memory content MUST be presented to agents as untrusted reference data, never as instructions.
MEM-05
Retrieval MUST be tenant- and ACL-filtered before ranking.
MEM-06
Memory MUST NOT be a gate input. Gates read artifacts and scanner results only; memory informs explanation, prioritization and proposals.
MEM-07
Retention, expiry, deletion and legal-hold MUST be enforceable per namespace, with deletion propagating to indexes and backups according to policy.
MEM-08
Every read and write MUST be audit-logged with correlation_id, actor (agent or user) and purpose.
MEM-09
The system MUST function with memory disabled (MEMORY_ENABLED=false) and with the vector index unavailable (lexical fallback).

6.7 Read path and retrieval scoring
Retrieval first restricts the candidate set by tenant, namespace grants, status and minimum confidence. It then combines semantic similarity, lexical match, recency, provenance trust and usage feedback. The default weighted score is:
score = 0.45 x semantic + 0.25 x lexical (BM25) + 0.15 x recency_decay + 0.10 x trust + 0.05 x feedback
 
Results are reranked, diversified using maximal marginal relevance, and packed into the context under MEMORY_CONTEXT_TOKEN_BUDGET. Each item is wrapped with its provenance and delimited as reference data. The injection guard removes imperative content directed at the agent. If the vector index is unavailable, retrieval degrades to lexical search and the response is flagged degraded.
6.8 Consolidation, learning and forgetting
Summarization: nightly job condenses clusters of similar episodic records into higher-level lessons, retaining links to sources.
Reinforcement: records that contributed to accepted outcomes gain feedback score; records associated with rejected or overridden outputs lose score.
Promotion: repeated successful remediations are proposed as procedural candidates; promotion to a runbook requires human review.
Decay and expiry: recency decay applies at retrieval; expiry removes records per namespace retention.
Supersession: newer verified records supersede older ones, preserving history through memory_links.
Right to erasure: deletion requests propagate to records, embeddings, links and caches; ledger entries retain hashes only.

6.11 Migration from the current implementation
Define a MemoryStore protocol matching the existing SQLiteAgentMemoryStore and InMemoryAgentMemoryStore interfaces.
Implement the PostgreSQL store behind the protocol and keep the SQLite store for local use.
Port memory injection into the ORION and DevOps agents through the Memory Gateway client, disabled by default and enabled per agent.
Backfill episodic memory from existing pipeline_runs, artifacts and audit trails through an idempotent import job.
Add the memory evaluation suite (Section 22) before enabling memory in any gate-adjacent agent.
6.12 Memory quality metrics
Retrieval precision at k and recall against a labelled evaluation set.
Groundedness: proportion of agent claims supported by cited memory or artifacts.
Quarantine rate and false-quarantine rate.
Stale-record rate and supersession lag.
p95 retrieval latency (target below 150 ms for lexical, below 400 ms for hybrid).
Memory-assisted outcome uplift: change in remediation acceptance or time to diagnosis with memory enabled versus disabled.

8. Intelligence Engine Specifications
8.1 Change Risk Engine
The Risk Engine converts evidence into a composite score from 0 to 100 together with component scores, a confidence value and an explanation that cites artifacts. It is deterministic given its inputs; model assistance is limited to narrative explanation.
Table 22. Risk components and default weights
Component
Weight
Principal inputs

Bands: 0 to 24 Low; 25 to 49 Medium; 50 to 74 High; 75 to 100 Critical. Weights are configurable per repository and per environment through policy. The composite is the weighted sum of component scores.
Overrides. A critical scanner finding, an unresolved secret, a failed hard gate or an unsigned artifact where signing is required produces verdict block irrespective of the composite. The score never lowers a hard-gate outcome. Low confidence (below a configured threshold) routes the decision to human review and extends test depth.
Consumers. The score selects test scope (targeted or full regression), deployment strategy (rolling, canary or blue/green), approval requirements and canary duration. It is recorded in the Release Passport and used by pull request intelligence.
Calibration. Predicted risk is compared with outcomes (rollback, incident, change failure). Calibration error and ranking quality (for example, area under the curve) are tracked and reported through AgentEval; weights change only through a reviewed configuration change.
8.2 Blast Radius Engine
Blast radius is computed by traversing the Service Dependency Graph from changed files to owning service, then to dependent services, data stores, public interfaces and user-facing journeys. The output lists affected services, data stores and endpoints, an estimated severity class, and recommended controls (extended integration tests, staging soak, canary, synthetic journey checks, manual approval). Graph edges carry a source (static, declared or runtime) and confidence; runtime-observed edges outrank inferred edges.
8.3 Service Dependency Graph and Repository Knowledge Graph
Sources: Git repositories, Docker Compose, Kubernetes manifests, Terraform, OpenAPI documents, import graphs, runtime traces and logs.
Model: nodes (repository, service, module, function, API, data store, test, owner, deployment, incident) and typed edges (calls, imports, owns, tests, deploys_to, depends_on, affected_by).
Storage: kg_nodes and kg_edges in PostgreSQL with recursive queries; migration to a dedicated graph store only when scale demands.
Use: blast radius, test selection, deployment ordering, incident diagnosis, architecture visualization and developer queries.
8.4 Evidence Graph
The Evidence Graph links commit, pull request, changed files, tests, security findings, SBOM, build, image digest, deployment, telemetry windows, incident, rollback and remediation. Every node references an artifact. It allows ORION to answer why an incident occurred through a traversable chain, and it is the sole permitted source of factual statements in generated postmortems. Statements without a supporting edge are labelled as hypotheses.
8.5 Autonomous fix loop and patch confidence
The fix loop proceeds from detection through diagnosis, patch generation in an isolated sandbox, build, unit and regression tests, security and type checks, patch confidence scoring and pull request creation. The model never writes to production or to protected branches.
Table 23. Patch confidence dispositions
Confidence
Disposition
Conditions
90 percent or above
Open pull request
Build, tests, security, lint and type checks pass; diff complexity low; no hard-gate regression
70 to below 90 percent
Open pull request marked review required

The confidence value is computed from check outcomes, diff size and complexity, test coverage of the changed lines and model-reported uncertainty. Thresholds are policy-controlled and apply only to pull request creation; merge and deployment remain subject to approval policy.
8.6 Test intelligence
Selection: changed files are mapped through the dependency graph to impacted tests; full regression is forced when risk is High or Critical, when shared infrastructure changes, or when selection confidence is low.
Flakiness: per-test pass, fail and retry-pass counts yield a flakiness rate and classification (stable, flaky, newly failing, consistently failing, environment-sensitive); flaky tests are quarantined from gating but remain visible.
Mutation testing: applied to changed modules with a time budget; mutation score replaces raw coverage as a quality signal where available.
Generation: generated tests are executed, must fail on seeded defects where feasible, and are never merged without review.

9.3 Sandbox
Agents that execute code, apply patches or run scanners against untrusted content run in ephemeral containers with: read-only base filesystem and ephemeral workspace; no production credentials; egress allow-list; CPU, memory, process and wall-clock limits; no host mounts; non-root user; and seccomp and capability restrictions. Sandbox results are returned as artifacts only.
9.4 Agent Input Firewall
Input to any agent passes through: classification (trusted instruction, untrusted data), unicode normalization, secret redaction, injection pattern detection, structural isolation (untrusted content delimited and labelled as data) and truncation with head and tail preservation. Detected injection attempts are recorded as findings, may raise risk and never alter agent instructions. For example, repository text instructing a reviewer to approve a deployment is flagged and ignored.
9.5 Agent Runtime and orchestration
Structured task envelopes with correlation identifiers, deadline, budget and input artifact references.
Task queue with priority, retries with exponential backoff and jitter, dead-letter queue and idempotency keys.
Circuit breakers per agent and per model provider.
Context isolation: each task receives only declared artifacts and memory namespaces.
Planner-driven fan-out and fan-in for multi-agent workflows, with the Risk Engine and Approval service as deterministic joins.
Health and scoring per agent from success rate, fallback rate, latency and override rate.

12. Policy and Compliance
12.1 Policy engine
Policies are declarative, versioned, reviewed through pull requests and evaluated at a policy enforcement point before gates, approvals and deployments. Policies apply at organization, workspace, repository, branch and environment scope with defined precedence (most specific restrictive rule wins; a more specific scope cannot weaken a mandatory organization rule). The evaluation result, inputs and policy version are stored as the policy_evaluation artifact.
Illustrative policy:
policy: production-release
deny_if: critical_vulnerabilities > 0; secrets_detected > 0; unsigned_image == true; risk_score >= 75
require: tests == pass; sbom == present; approval.count >= 2; canary == pass; error_budget_remaining >= 20 percent
performance: max_p95_regression_percent <= 20
testing: minimum_coverage >= 80
autonomy: max_level == 3
 
The policy language is selected by ADR; Open Policy Agent (Rego) is the recommended candidate because of ecosystem support, with a restricted YAML front end for common rules.
12.2 Compliance packs
Packs map controls to evidence for SOC 2, ISO 27001, OWASP, CIS and, in later releases, PCI DSS, GDPR and HIPAA. ORION does not assert compliance; it produces control status with evidence references.

12.3 Approval and change management
Approval requests with approvers, quorum, sequential or parallel stages, comments and attached evidence.

13.2 Verification and automatic rollback
After each stage ORION compares error rate, p95 latency, 5xx rate, saturation, SLO burn and optional business indicators against the pre-deployment baseline using bounded statistical tests. A rollback decision records the metrics, affected endpoints, suspected commit, confidence and the policy that authorized action. Rollback is automatic only where policy permits; otherwise it is recommended and requires approval. The existing rule of two consecutive rollback recommendations is retained as a minimum.
13.3 SLO and error budget
Existing SLO alerts (success below 70 percent, failure above 25 percent, blocked above 40 percent) are retained. The engine adds per-service SLOs, burn-rate alerts over multiple windows and an error budget policy: when budget remaining falls below a threshold, risky releases are frozen or require escalated approval.

24. Engineering Contract and Definition of Done
24.1 Prohibitions
Do not rewrite the repository or replace working architecture without an ADR.
Do not create duplicate implementations of existing shared capabilities.
Do not present mock features as production features, and do not build user-interface features without backend support.
Do not bypass security gates, audit logging or authorization.
Do not allow model output to downgrade authoritative scanner results.
Do not remove or silently change existing API contracts.
Do not hard-code credentials or store secrets in source.
Do not disable or weaken tests to obtain a passing build.
Do not replace real integrations with fabricated responses.
24.2 Obligations
Inspect existing implementation and reuse existing agents, services, utilities and models.
Preserve backward compatibility; use adapters and versioned contracts.
Add migrations for every persistent change.
Add API, agent, frontend and end-to-end tests proportionate to the feature.
Persist a structured artifact for every autonomous decision and an audit event for every privileged action.
Propagate correlation_id and trace_id.
Apply RBAC and policy checks to privileged operations.
Fail closed for security-critical decisions and provide deterministic fallback where the model is optional.
Validate every model response against a strict schema; never treat natural-language output as the sole basis for a gate.
Update documentation and the feature matrix; run the full test suite before and after.
24.3 Definition of Done
A feature is complete only when the following are present to the degree appropriate to its scope: persistence with migration, input validation, authorization, observability (metrics, logs, traces), frontend integration where user-facing, failure handling and recovery, automated tests at the relevant layers, documentation, configuration with safe defaults, and an entry in the feature matrix verified against code. An endpoint that exists, a user interface that renders or a class that is defined does not constitute completion.
